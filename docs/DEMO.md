# A three-minute MAYA walkthrough

MAYA is a separate post-code delivery service. Field Supply is the ecommerce company
that uses it. The GitLab Duo Agent Platform provides actual reasoning; MAYA owns
observation, evidence, permissions and verified delivery.

## What to show

1. **Company and policy (20 seconds).** Open the hosted console, sign in with the
   existing Render operator key, and select Field Supply. Open Connections & policy:
   discovered source, stack, six pipeline jobs, `.maya.yml` staging boundary and live
   revision endpoint. Tokens stay server-side. A repo URL discovers configuration;
   external tools still need separate credentials.
2. **A real failed push (25 seconds).** Select a CI failure in Delivery history.
   Open Original failure and `unit_tests.log`: these are real GitLab jobs and original
   assertions. The source evidence names the immutable commit and blob identity.
3. **Workforce and actual source repair (45 seconds).** Click Investigator, Fixer
   and Verifier. Open the real Duo session, then Review file changes. Show the actual
   original/replacement diff and unchanged tests. The first example uses separate
   operator publication and merge decisions; supervised staging follows an explicitly
   enabled repository policy.
4. **Proof before fixed (35 seconds).** Open the repair MR and exact-commit CI.
   Show staging merge/release checks, successful deployment and expected/observed full
   Git SHA. A green MR or HTTP 200 alone cannot resolve a delivery.
5. **Reviewed memory (30 seconds).** Show the first lesson, its raw provenance,
   operator review and retired previous version. In a later failure, show the actual
   matched lesson ID and fresh source/log evidence. This is advisory retrieval,
   not model retraining or permission to reuse an old patch.
6. **A separate stack (20 seconds).** Switch to Signal Desk, the Python/FastAPI
   company using GitHub Actions and Render. Show its real repair PR #1, green CI,
   verified full live SHA and reviewed lesson. Its source, credentials and memory
   are separate from Field Supply. These are two configured provider paths;
   other tools still need integrations and access.

## Narration

“Teams already have source, tests and staging. When a push breaks delivery, MAYA
collects what actually failed and asks a GitLab Duo workforce for a source repair.
It opens a real MR, follows the exact repair commit through CI, and verifies which
commit reached staging. Reviewed company lessons guide the next investigation.
Every decision has inspectable evidence.”

## Honest demo labels

The source defects are deliberately introduced stimuli. GitLab/GitHub CI failures, Duo
sessions, source edits, MRs/PRs and deployments are real. Automated tests with fake
provider transports validate controller behaviour separately. Production deployment,
universal company integration and model self-training are not demonstrated.
The older fault-reset lab is explicitly at `/?lab=1`.

Company B's history retains three failed or incomplete investigations while MAYA's
prompt sizing, evidence selection and a credential-filter false positive were fixed.
Its eventual application repair was authored by Duo. Checkpoint recovery was an
administrative intervention. Do not describe this rollout as an uninterrupted
autonomous run. Automatic repair currently begins with a failure at the current
default staging branch, not an unmerged feature PR.

Free Render may sleep. Wake the service before recording. Export workspace evidence
before a demonstration. Encrypted checkpoints recover this demo's operations records;
a persistent production database is still needed for stronger durability.

Do not reset a history to make the demo look cleaner. Use the recorded failures,
retired lesson, actual MRs and verification trail. Do not expose operator keys,
provider tokens or raw Render Environment pages in the video.
